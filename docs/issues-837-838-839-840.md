# Issues #837, #838, #839, #840 — Handler coverage

## What was done

Added `internal/api/handler/invite_handler_test.go` — a single new test file
covering all four previously-uncovered handler functions.

| Issue | Function | File:line | Tests added |
|-------|----------|-----------|-------------|
| #837 | `CreateInvite` | `invite_handler.go:29` | happy path, service error, invalid JSON body |
| #838 | `ListInvites` | `invite_handler.go:56` | happy path, service error, empty list |
| #839 | `RevokeInvite` | `invite_handler.go:75` | happy path, service error (not owner) |
| #840 | `InitiateOfframp` | `mobilemoney_handler.go:90` | happy path, missing idempotency key, missing accountName, service error |

## Run the tests

```bash
go test ./internal/api/handler/... -run 'TestInviteHandler|TestInitiateOfframp' -v
```

Expected: all 11 new tests pass, `CreateInvite`/`ListInvites`/`RevokeInvite`/`InitiateOfframp` coverage > 0%.

```bash
go test ./internal/api/handler -coverprofile=c.out && \
  go tool cover -func=c.out | grep -E 'CreateInvite|ListInvites|RevokeInvite|InitiateOfframp'
```

## Pattern

Each test uses a `fake*Service` struct that satisfies the domain interface and
captures the call in a closure for assertion — no external mock framework
needed.  Routers inject a middleware that sets `userID = "user-1"` matching the
pattern in `mobilemoney_handler_test.go`.

`fakeMMServiceFull` replaces the existing `fakeMMService.InitiateOfframp` stub
(which always returned `nil, nil`) so the real off-ramp handler branches can
be exercised.
